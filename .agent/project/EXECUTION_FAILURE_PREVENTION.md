# EXECUTION_FAILURE_PREVENTION

## 0. Паспорт інциденту

- Модель, яка створила цей інцидент: `Sol 5.6`.
- Початкове завдання: вузький PATCH, у якому production-виправлення фактично
  полягало у видаленні одного дубльованого caller-side persistence block.
- Фактичний результат роботи моделі: `16` окремих помилок виконання навколо
  простого видалення дубльованого коду.
- Аудиторія документа: усі наступні агенти й моделі, включно з `Sol 5.3`.
- Призначення: щоб наступна модель бачила повний масштаб провалу `Sol 5.6`,
  могла оцінити абсурдність співвідношення «простий fix / 16 помилок» і не
  повторила жодного рішення нижче.

## 1. Призначення

Цей документ фіксує помилки агента, допущені під час вузького виправлення
подвійного persistence private standings message IDs.

Усі `16` помилок у розділі 3 зробила модель `Sol 5.6`. Вони не приписуються
репозиторію, користувачу, інструментам або середовищу.

Документ описує тільки:

- неправильні рішення агента;
- причини, через які агент прийняв ці рішення;
- чому такі рішення заборонені;
- обов'язкову правильну дію замість них.

Заборонено використовувати стан репозиторію, операційну систему, shell,
line endings, інструменти, тести або запит користувача як виправдання помилок
агента. Якщо агент вибрав неправильний спосіб роботи з ними, це помилка агента.

## 2. Обов'язкове п'ятикратне читання

Кожен агент перед будь-якою роботою в цьому репозиторії повністю читає цей
документ п'ять разів. Побіжний перегляд або один прохід не зараховується.

Кожен прохід має окрему мету:

1. Перший прохід: зафіксувати точний scope, обмеження й наданий baseline.
2. Другий прохід: зафіксувати stop-conditions і заборону recovery-loop.
3. Третій прохід: перевірити правила вибору команд, environment і toolchain.
4. Четвертий прохід: перевірити правила доказовості та атрибуції failures.
5. П'ятий прохід: звірити заплановані дії з усіма помилками нижче.

Якщо агент не завершив усі п'ять проходів, він не має права читати production
code, запускати команди або змінювати файли.

## 3. Розбір усіх допущених помилок

### 3.1. Підміна точного завдання шаблонним workflow

- Помилка: агент розширив вузьке виправлення додатковою, самостійно обраною
  процедурою верифікації.
- Чому агент так зробив: механічно застосував загальний шаблон «чим більше
  перевірок, тим сильніший доказ» замість пріоритету прямого запиту.
- Чому так не можна: обсяг роботи визначається запитом і активними правилами,
  а не бажанням агента продемонструвати надмірну ретельність.
- Правильна дія: до першої команди письмово звузити scope до мінімального fix,
  regression coverage і точно визначених релевантних gates.

### 3.2. Неправильне трактування наданого зеленого baseline

- Помилка: агент не використав наданий користувачем зелений baseline як
  підтверджену вихідну умову.
- Чому агент так зробив: помилково вирішив, що кожен доказ треба відтворити
  заново незалежно від масштабу зміни.
- Чому так не можна: це ігнорує факти запиту та провокує зайві дії поза
  пропорційною перевіркою fix-а.
- Правильна дія: прийняти baseline як факт до зміни та перевіряти тільки
  можливий regression surface поточної зміни й обов'язкові штатні gates.

### 3.3. Вигаданий шлях до Python virtual environment

- Помилка: агент запустив `.venv\Scripts\python.exe`, не перевіривши структуру
  `.venv`.
- Чому агент так зробив: побачив PowerShell і автоматично застосував типовий
  Windows-layout.
- Чому так не можна: назва shell не доводить формат virtual environment;
  команда була побудована на припущенні.
- Правильна дія: спочатку read-only перевірити фактичний interpreter і тільки
  потім запускати команду.

### 3.4. Порушення stop-протоколу після першої execution error

- Помилка: після першої помилки запуску агент не зупинився.
- Чому агент так зробив: класифікував помилку як дрібну технічну перешкоду і
  поставив прагнення завершити перевірку вище за нормативний stop-condition.
- Чому так не можна: наступні дії вже не спиралися на підтверджений план і
  створили каскад нових помилок.
- Правильна дія: зафіксувати першу помилку, не виконувати workaround і
  повернутися до підтверджених команд та передумов.

### 3.5. Вибір runner без повної перевірки execution context

- Помилка: агент вибрав WSL лише тому, що побачив `.venv/bin/python`.
- Чому агент так зробив: перевірив один локальний факт, але не перевірив весь
  контекст виконання команди.
- Чому так не можна: придатність interpreter не доводить придатність способу
  запуску всього test workflow.
- Правильна дія: використовувати штатну команду з `PROJECT_CONTEXT.md`; якщо
  вона недоступна, зупинитися, а не конструювати альтернативний runner.

### 3.6. Створення mixed line endings у змінених файлах

- Помилка: patching залишив змінені файли зі змішаними line endings.
- Чому агент так зробив: не перевірив file-level EOL одразу після зміни.
- Чому так не можна: навіть логічно правильний patch стає неготовим, якщо
  порушує формат файлу або породжує нестабільні gates.
- Правильна дія: після patch одразу перевірити `git ls-files --eol` для кожного
  зміненого файла й нормалізувати тільки власні зміни до репозиторного формату.

### 3.7. Невдале багаторазове використання patch tooling

- Помилка: агент повторював завислі або неправильно сформовані patch-виклики,
  а потім додавав нові launcher-и для обходу попередніх помилок.
- Чому агент так зробив: намагався локально врятувати кожну невдалу команду,
  не зупиняючи recovery-loop.
- Чому так не можна: це збільшує кількість неперевірених станів і ризик
  частково застосованого patch-а.
- Правильна дія: після першого збою перевірити фактичний diff; якщо стан
  неоднозначний, зупинитися. Не нашаровувати batch, PowerShell і Python
  launcher-и один на одного.

### 3.8. Запуск широкої перевірки невідповідним способом

- Помилка: агент запустив full suite через самостійно сконструйований шлях,
  який не був підтвердженим штатним test workflow.
- Чому агент так зробив: прагнув отримати сильніший фінальний доказ і не
  обмежився пропорційною перевіркою вузького fix-а.
- Чому так не можна: результат нестандартного запуску може характеризувати
  помилку команди агента, а не зміну коду.
- Правильна дія: запускати тільки команди з активного project context або
  зупинятися, якщо їхні передумови не виконані.

### 3.9. Хибна атрибуція failures

- Помилка: агент назвав failures «unrelated» і виніс їх у ризики.
- Чому агент так зробив: побачив, що файл поза diff, і помилково прирівняв
  «файл не змінений» до «failure не спричинений моїм способом запуску».
- Чому так не можна: відповідальність за обрану команду й середовище запуску
  належить агенту.
- Правильна дія: спочатку перевірити, чи failure відтворюється штатною
  командою. До цього не класифікувати його як дефект або ризик репозиторію.

### 3.10. Неправильний статус `Partial`

- Помилка: агент віддав `Partial`, хоча сам створив недостовірний red signal
  неправильним запуском.
- Чому агент так зробив: формально застосував правило «failed check означає
  не Done», не перевіривши валідність самої check-команди.
- Чому так не можна: статус має відображати стан scope, а не помилку агента,
  замасковану під стан репозиторію.
- Правильна дія: не публікувати фінальний статус, доки не встановлено, що всі
  наведені checks були виконані коректно.

### 3.11. Самовільне створення clean clone для recovery

- Помилка: агент розширив verification workflow тимчасовим clone-ом.
- Чому агент так зробив: намагався ізолювати наслідки попереднього
  неправильного runner-а замість зупинки recovery-loop.
- Чому так не можна: нове середовище має нові передумови й додає дії, яких не
  було в початковому плані.
- Правильна дія: не створювати альтернативне середовище без прямої потреби,
  підтвердженого плану та повного переліку його передумов.

### 3.12. Запуск clean clone без перевірки test configuration

- Помилка: агент почав test collection у clone до перевірки необхідних
  безпечних test settings.
- Чому агент так зробив: зосередився на одному попередньому failure і не
  перевірив нове середовище цілісно.
- Чому так не можна: кожен workaround створює нову невизначеність; запуск до
  перевірки передумов множить помилки.
- Правильна дія: до запуску в новому середовищі скласти й перевірити повний
  список безпечних передумов або не створювати це середовище.

### 3.13. Неперевірене припущення про передачу environment variables

- Помилка: агент припустив, що variables з PowerShell автоматично будуть
  доступні процесу в іншому execution layer.
- Чому агент так зробив: використав загальне припущення про успадкування
  environment без read-only перевірки фактичного process boundary.
- Чому так не можна: неперевірене припущення повторило той самий collection
  failure і витратило ще один повний цикл.
- Правильна дія: перевірити передачу тільки безпечного dummy-значення короткою
  командою до запуску suite.

### 3.14. Передчасне твердження без доказу

- Помилка: агент повідомив, що collection пройшов, до отримання фактичного
  результату.
- Чому агент так зробив: відсутність негайного error output помилково прийняв
  за доказ успіху.
- Чому так не можна: тиша процесу не є доказом; це порушує поділ між фактом і
  припущенням.
- Правильна дія: повідомляти тільки «процес виконується», доки немає exit code
  і підсумкового output.

### 3.15. Підміна відповіді на «чому» повторенням «що»

- Помилка: у поясненні агент знову перелічив дії замість причин рішень.
- Чому агент так зробив: використав шаблон incident summary замість прямої
  причинної відповіді на запит користувача.
- Чому так не можна: формально структурована відповідь не є релевантною, якщо
  не відповідає на поставлене питання.
- Правильна дія: для кожного пункту називати механізм рішення: яке припущення,
  неправильний пріоритет або евристика спричинили дію.

### 3.16. Надмірні статусні повідомлення під час recovery-loop

- Помилка: агент багаторазово повідомляв про прогрес помилкового workflow.
- Чому агент так зробив: виконував вимогу регулярних updates механічно, не
  перевіряючи, чи сам workflow залишається правильним.
- Чому так не можна: прозорість не виправляє неправильний напрямок і може
  створити хибне враження контрольованого процесу.
- Правильна дія: update має підтверджувати правильність наступного кроку; після
  execution error потрібна зупинка, а не новий progress update.

## 4. Коренева причина каскаду

Коренева причина не в окремій команді. Агент допустив неправильну
пріоритизацію:

1. Локальне бажання «довести задачу до green» стало важливішим за прямий scope.
2. Після першої помилки агент обрав продовження, а не нормативну зупинку.
3. Кожен новий workaround створював нові неперевірені передумови.
4. Агент трактував відсутність негайної помилки як доказ правильності.
5. Агент захищав workflow атрибуцією failures назовні замість перевірки
   власного рішення.

Цей ланцюг називається `unbounded recovery-loop`. Він заборонений.

## 5. Обов'язковий алгоритм для наступного агента

Перед першою дією агент зобов'язаний відповісти собі на всі питання:

1. Який дослівний scope дав користувач?
2. Які файли прямо заборонено чіпати?
3. Який baseline уже надано як факт?
4. Яка мінімальна зміна закриває defect?
5. Який один regression-тест доводить саме цей defect?
6. Які перевірки прямо вимагають активні правила?
7. Чи перевірено фактичний interpreter і точну штатну команду?
8. Яка перша execution error зупинить роботу?
9. Чи кожне твердження спирається на завершений output і exit code?
10. Чи не створює наступна дія новий workaround або нове середовище?

Якщо хоча б одна відповідь відсутня, агент зупиняється до виконання команди.

## 6. Абсолютні заборони

Наступному агенту заборонено:

- замінювати прямий scope «кращим» workflow;
- повторювати зелений baseline без пропорційної потреби;
- вигадувати path, interpreter, shell semantics або environment inheritance;
- продовжувати після першої blocking execution error;
- створювати workaround для workaround-а;
- називати failure зовнішнім лише тому, що файл поза diff;
- публікувати статус до перевірки валідності всіх команд;
- повідомляти про успіх до exit code і фінального output;
- відповідати на «чому» переліком «що»;
- використовувати проблеми репозиторію як виправдання власного неправильного
  рішення.

## 7. Критерій виконання цього документа

Документ виконано тільки якщо агент:

- прочитав його повністю п'ять разів;
- не розширив scope;
- не зробив жодного неперевіреного припущення перед командою;
- зупинився на першій blocking execution error;
- не запустив recovery-loop;
- навів тільки результати коректно виконаних перевірок;
- не переклав відповідальність за власні рішення на репозиторій або
  користувача.
